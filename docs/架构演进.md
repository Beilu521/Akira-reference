# 架构演进:从单机 Agent 到日志分析平台

> 面试高频题:"你这套东西,日志量涨 100 倍怎么办?"
> 这份文档就是答案的骨架。每一级都写清楚:**先坏什么 → 怎么换 → 代码里哪里已经留好了缝**。
> "留好了缝"是关键——架构演进不是重写,是把接口后面的实现换掉。

## 现状基线(单机版)

| 项 | 数字/事实 | 出处 |
|---|---|---|
| 规则匹配吞吐 | ~60 万行/秒(单核,10 万行 166ms) | `akira eval --scale 100000` |
| 正则匹配延迟 | 预编译 ~1.4µs vs 逐次编译 ~13.7µs(10 倍);50 条规则下分类匹配比朴素快 ~1.6 倍 | `internal/detector/bench_test.go` |
| 深度分析成本 | 每次 1 条 LLM 调用链(秒级、花钱) | `internal/llm/client.go` |
| 存档 | SQLite 单文件 | `internal/storage/` |

**核心结论:当前架构真正的成本中心是 LLM 调用,不是日志处理。**
正则匹配每秒 60 万行,LLM 一轮对话要几秒、还烧钱。所以聚合(Aggregator)、冷却(Dedup)、
串行 worker、只把命中行喂给 LLM——这些设计全部是在保护 LLM 这个瓶颈。面试讲架构先讲这句。

## 阶段 1:单机多文件(日志量 ×10)

**先坏什么**:watcher 一次只 tail 一个文件;一台机器上有 N 个服务就有 N 份日志。

**怎么换**:多个 `watcher.New(path).Tail()` 实例 + 一个 fan-in 合流行流,检测循环不变。

**代码缝隙**:`watcher` 只对外吐 `chan string`,职责单一就是为这一步留的——
main 里加一个 `merge(chans ...<-chan string) <-chan string` 即可,`detector.HotEngine` 和 worker 一行不改。

## 阶段 2:采集与分析分离(×100)

**先坏什么**:同一进程既 tail 又调 LLM。分析高峰拖慢检测;进程一崩,检测和分析两头全丢。

**怎么换**:拆成两个角色——
- **采集端**(轻):tail + 规则匹配 + 告警聚合,命中后写进队列而不是本地 channel
- **分析端**(重):独立进程,消费队列,调 LLM,回写结论

中间队列:Redis Stream / Kafka。**代码缝隙**:`pendingAnalysis` 通道天然就是队列的本地替身,
把 `analysisCh <- pendingAnalysis{...}` 换成"生产到队列"、worker 换成"消费队列",
`agent.Run` 的调用方式一个字不用动。`Serve` 模式已经在朝这个形态走(检测/分析可分进程调用)。

## 阶段 3:存储专业化(×1000)

**先坏什么**:SQLite 单机写锁,并发写多了顶不住;TF-IDF 全量扫描在百万条历史下变慢。

**怎么换**:
- 告警明细 → PostgreSQL / ClickHouse(时序聚合后者更强)
- 全文/相似检索 → Loki / Elasticsearch,或 embedding + 向量库(见 Roadmap)
- 本工具退化为"检测 + 转发",自己不再存历史

**代码缝隙**:`storage.Store` 是接口(`Save/UpdateReport/Recent`),
换 PG 就是写一个 `PgStore` 实现它;`tools.HistoryStore` 也是接口,相似检索的
TF-IDF 实现可以换成"调 ES"——Agent 拿到的工具签名不变。

## 阶段 4:检测能力升级(规则维护成本爆炸时)

**先坏什么**:规则条数涨到几百条后,人工维护正则的成本超过收益;未知异常模式正则根本覆盖不到。

**怎么换**:两层检测——
1. 日志模板提取(如 Drain 算法)自动聚类出"正常模板",偏离模板的行才进规则/LLM
2. LLM 兜底判断新模式是不是异常,确认后沉淀为新规则(规则自动生长)

**代码缝隙**:`detector.Engine` 是接口形状的东西,换成一个"模板聚类 + 正则"的混合实现,
`Match(line) []*Match` 的契约不变——下游(聚合/告警/评测)全部无感。

**评测框架在这个阶段价值最大**:每换一种检测算法,同一份标注集(`eval --scale`)跑一遍,
精确率/召回率/吞吐三个数字说话。没有评测的检测系统,任何"优化"都说不清是变好还是变坏。

## 面试 30 秒版

> "我的 Agent 是单机形态,但我把会变的部分全收在了接口后面——存储是 Store 接口,
> 分析输入是 channel(天然对应消息队列),检测是 Engine。日志量涨 100 倍时,
> 先坏的是采集和存储,不是 Agent 逻辑:tail 换 Kafka 消费、SQLite 换 ClickHouse,
> Agent 循环一行不改。真正的成本中心是 LLM 调用,所以聚合、冷却、串行化这些设计
> 全是在保护它——而且我用评测框架量化过:规则匹配 60 万行/秒,LLM 才是瓶颈。"

## 诚实声明

以上演进路径是**设计推演**,不是已验证的生产事实——本项目的实测范围是单机 10 万行级。
但接口缝隙是真实存在于代码里的(每一节都给了落点),这正是"为演进留缝"和"空谈架构"的区别。
